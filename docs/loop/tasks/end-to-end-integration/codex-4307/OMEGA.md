# Where Omega fits in UOR-R4

The public Omega material describes a programming language, a compiler, multiple hardware backends, model runners, a transformer trainer, specialist models and an associative predictor. The workloads have different inputs, denominators and correctness checks. All hardware results below are Drake's team's measurements. This review checked the underlying descriptions, several source implementations and the receipts. They have not been independently rerun on Wick.

The source snapshot inspected on 26 November 2026 was Omega core `2db0ef400e8e3558c42937a86eb56c2ca1a858e1`, canonical Helix `3a223392468fc54e577596a6afefb9908768f50d` and the GitHub Helix mirror `73fa04e6d27f8a8fb535f67a47ac4124ee5c490e`. Core and Helix publish Apache-2.0 source. Model weights and data have separate licenses. The survey covered the 39 HTML destinations in the public site map, all four strand pages, Helix, Arboris, bootstrap, language guide and knowledge base, the online compiler, the SI and SI 2.0 status pages, research and direct forge receipts. The site index and website claims sometimes lag later source receipts. ## Proposed exchange with Drake

The existing `protocol/uor-gpu` directory is a better starting point than a new framework partnership. It binds source, compiler, payload, proof and replay to a signed artifact. Its recorded payloads are eight-element unsigned integer vector addition on an SM121 binary interpreter and float vector addition on a SPIR-V interpreter, including boundary canaries. This specific bundle path still lists physical GB10 execution as pending. Other Omega models have physically run on GB10. [UOR/Prism bundle at the inspected commit](https://interplane.io/drakestapleton/omega-mv/blob/2db0ef400e8e3558c42937a86eb56c2ca1a858e1/protocol/uor-gpu/README.md)

1. **Offer a genuine R4 operator.** Supply a versioned public fixture for the existing two-token XOR/popcount Pick read, including exact input codes, original token IDs, causal boundary, duplicate occurrences, latest-occurrence tie, no eligible predecessor and successor at the boundary. Include sign, overflow or saturation cases for any additional integer mixture operator. Provide Rust/D11 expected outputs and a deliberately wrong trace. The receipt should bind the operator, expected results, shapes, artifact and version. A stateful memoization key must include model/optimizer generation and relevant carry or cache state.
2. **Build one comparable backend.** First compare Omega replay against the reference on the same bytes. Next run physical AOT code on an explicitly supported target and compare every selected index, token and state word. SM89 availability and a browser integer target are deliverables to establish. A GB10 result can establish GB10 behavior while Wick continues with the charter-approved Rust/nvcc path. Any change to §3 or the approved build path requires the owner's decision before product promotion.
3. **Measure a useful speedup.** Profile the original application first. Time a resident batch, data transfer and compilation/cold start separately, then time the entire unchanged training or inference job. Match hardware, work, precision, clock/power conditions, initial state and outputs. Report warm and cold curves, activation and resident bytes, throughput, joules per token when metered, and wall time to the same quality. A kernel consuming 10% of wall time, sped up tenfold, improves the whole run by about 1.10×. Retain the reference if total cost is unchanged.
4. **Let a native Omega mechanism compete for the model role.** If Drake has a learned sparse integer operator, compare it with P4/P5 on text-only unassisted prediction, same train/held split, bytes, budget and hardware. A reproducible held-quality and product advantage earns replacement of the measured stage. A full alternate model merits an independent decision on the same product tasks and resource limits. A backend that preserves exact state can improve speed with identical quality. These tests make either outcome useful for both groups.

### A public operator fixture from this review

The [five-vector Rust fixture](pick_fixture.rs) calls the existing [P4 Pick source](../../../../../crates/uor-r4-discrete/src/kn_ceiling/runtime/code_pick.rs) directly. It checks insufficient context, a unique exact occurrence, a tie with two different successor tokens, a tie with identical successor tokens at distinct addresses, and a nonzero Hamming-distance winner. For the prefix `10 11 12 10 11 12 10 11`, the expected read is occurrence 4, distance 0, two ties, successor address 5, token 12. Choosing occurrence 1 and successor address 2 also returns token 12 and fails the fixture.

Five of five passed on an Apple M1 running the host executable and in Chrome 158.0.8127.38 executing the same Rust source compiled to Wasm32. The Wasm module had zero imports and ran from an embedded local page. A separate wrong-address expectation retaining token 12 failed on the host and trapped in the browser. Rust was 1.97.1. The production operator source SHA-256 was `2fcd68794ecbe0498a6e3de7e3431d3d0eb85ec4bc1162a9c5ef3c59be54ade3`. To repeat, compile the fixture with `rustc --edition=2021 -C opt-level=1`, run it, then compile the same file with `--target wasm32-unknown-unknown` and invoke its exported `main(0,0)` from the browser. The fixture uses synthetic integer codes, loads no model and measures no timing. Omega compilation, physical GPU comparison and whole-model browser inference remain open.

The concrete questions for a collaboration are the available physical SM89/Metal/Wasm receipts for the same integer operator, the reuse terms for those components, the trace and memory ABI, and which run Drake would accept as evidence against deploying a proposed optimization. No Omega binary or driver was run for this review.
